# Prompt: Supabase Database and Data Access

## Goal

Implement the initial Supabase persistence foundation for Skew News: a reproducible
SQL schema for the six required core tables, explicit grants and Row Level Security,
typed Supabase clients with a strict browser/server boundary, and small data-access
modules for public news reads and service-role pipeline operations.

This task establishes persistence and query APIs only. Do not replace the current UI
fixtures, add scraping, run AI analysis, implement scheduler HTTP integration, add API
routes, or enable pgvector/embeddings in this phase.

## Decisions and assumptions

- **Initial schema only:** follow section 7 of `AGENTS.md`; do not add the
  `article_analyses.embedding vector(1536)` column or related-article similarity
  function/index until the pgvector phase in section 20.
- **Schema workflow:** because no declarative `supabase/schemas/` configuration
  exists, use a checked-in imperative baseline SQL file at `supabase/schema.sql`.
  Also provide an initial migration containing the same schema so future environments
  can be reproduced. Since the Supabase CLI is unavailable, use a deterministic
  UTC timestamped migration filename based on implementation time and document that
  it was created manually rather than claiming CLI-generated migration history.
- **Remote execution:** no authenticated Supabase MCP/CLI database connection is
  available in this task. Do not claim the remote database was modified. Deliver SQL
  that the user can run in Supabase Dashboard -> SQL Editor, plus exact verification
  queries and REST smoke-test steps.
- **IDs:** use UUID primary keys generated by Postgres for application records.
  Oxylabs `schedule_id`, run IDs, and job IDs must be `text`, never JavaScript numbers,
  because they may exceed `Number.MAX_SAFE_INTEGER`.
- **Timestamps:** use `timestamptz` in UTC with `now()` defaults. Use
  `published_at`, `scraped_at`, `analyzed_at`, `created_at`, and `updated_at` where
  appropriate. Do not add update triggers merely for convenience; write paths set
  `updated_at` explicitly when updating.
- **Analyses:** enforce exactly zero or one analysis row per article by making
  `article_id` the primary key. Store `bias_score` as required by the product and
  enforce consistency with `(right_percentage - left_percentage) / 100` using a
  numeric check constraint. Enforce valid labels, score/confidence ranges, integer
  percentage ranges, and an exact percentage total of 100.
- **Public access:** signed-out readers need published analyzed news. Grant `SELECT`
  only to `anon` and `authenticated` on `sources`, `articles`, and
  `article_analyses`, with RLS policies limiting sources to active rows and articles
  to rows whose `analyzed_at` is not null. Analysis rows are visible only when their
  parent article is visible. Revoke all client-role access to `logs`,
  `oxylabs_schedules`, and `oxylabs_schedule_runs`.
- **Writes:** all inserts/updates for scraping, analysis, logging, and scheduling use
  the server-only service-role client. No client-role mutation policies are added.
- **Clerk boundary:** do not introduce Supabase Auth or attempt to pass Clerk sessions
  to Supabase. The browser/anonymous client is for public read access only.
- **Client separation:** expose a typed public client backed by
  `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and a separate
  `server-only` service client backed by `SUPABASE_SERVICE_ROLE_KEY` with Supabase
  Auth session persistence, refresh, and URL detection disabled.
- **Query errors:** query helpers return typed data and throw contextual `Error`
  instances on Supabase failures; they must not swallow errors or return untyped
  `any` values. Never include keys, request headers, or complete sensitive payloads
  in error messages.
- **URL checks:** the existing-URL query helper accepts original/canonical URLs,
  normalizes empty input, deduplicates it, and sends `.in()` filters in chunks of no
  more than 15 values. Avoid the documented joined-table `.eq()` filter gotcha;
  filter joined data in JavaScript where required.
- **No seed URLs:** do not seed sources or invent source homepage URLs. Source records
  will be managed in Supabase after the schema is applied.

## Database schema requirements

- Create `public.sources` with: UUID `id`, non-empty `name`, unique non-empty
  `listing_url`, optional `parser_strategy` as `jsonb`, `is_active`, optional
  `logo_url`, and timestamps.
- Create `public.articles` with: UUID `id`, required `source_id` foreign key, unique
  non-empty `original_url`, optional `canonical_url`, non-empty `title`, required
  non-empty `image_url`, required `published_at`, non-empty `raw_text`, `scraped_at`,
  nullable `analyzed_at`, and timestamps. Use a partial unique index for non-null
  canonical URLs. Keep articles append-only in query helpers.
- Create `public.article_analyses` with one row per article and every section 19
  analysis field: summary, sentiment score/label, stored derived bias score, framing
  label, left/center/right percentages, confidence, framing notes, loaded terms as
  `text[]`, disclaimer, model, and timestamps. Do not add embedding yet.
- Create `public.logs` for structured pipeline/server logging with a constrained log
  level, event/operation name, message, optional source/article references, `jsonb`
  context, and `created_at`. Foreign-key deletion must not erase operational history;
  nullable references should use `ON DELETE SET NULL`.
- Create `public.oxylabs_schedules` with a one-to-one active-source association,
  exact string `schedule_id`, state/status, sync/run timestamps, optional error and
  metadata, and timestamps.
- Create `public.oxylabs_schedule_runs` with its schedule relation, exact string
  external run/job IDs, result/processing status, result timestamps, processed time,
  error, summary/metadata JSON, and timestamps. Add uniqueness that prevents the
  same external job from being processed twice.
- Add indexes for active-source selection, article feed/detail/dedupe and pending
  analysis lookups, logs by recency/operation, schedules by source/external ID, and
  runs by schedule/status/recency. Avoid redundant indexes already supplied by PK or
  unique constraints.
- Make foreign-key delete behavior explicit and safe: prevent source deletion while
  articles exist; cascade an article deletion only to its analysis; retain logs with
  null references; cascade a deliberately deleted schedule row to its run-tracking
  children.
- Enable RLS on all six public tables, revoke client-role privileges before granting
  minimum read privileges, and create narrowly named `SELECT` policies only for the
  three public-content tables. Do not create permissive mutation policies.
- Grant the service role the operations needed by the data layer. Do not change
  project-wide default privileges as part of this app-specific baseline.
- Keep SQL safe to execute once in a new project. Do not use destructive drops,
  truncate statements, hardcoded source records, or fake application data.

## Data-access requirements

- All Supabase clients must use `createClient<Database>()`.
- Public query results should use explicit column lists rather than unrestricted
  `select('*')`, especially for joins and UI-facing shapes.
- Define clear result types for article summaries/details with nested source and
  analysis data. Normalize Supabase's to-one relationship result shape without
  `any` or unsafe blind casts.
- Public feed/detail helpers return only analyzed articles, order deterministically
  by published date then ID, and accept bounded limits. Detail lookup should use the
  current UUID ID because the schema has no product-approved slug field.
- Source selection helpers return active rows only and do not hardcode sources.
- Mutation helpers must import the service client from the server-only module and
  accept typed Insert/Update inputs narrowed to fields callers may legitimately set.
- Article insertion must be append-only and surface duplicate URL conflicts cleanly;
  no delete/reset/replace helper is allowed.
- Existing URL checks must honor the maximum 15 URL values per `.in()` request and
  check both original and canonical URL matches.
- Analysis writes should upsert on the one-to-one `article_id`, validate database
  error handling, and update `articles.analyzed_at` only through a separately named
  completion helper so later analysis orchestration can call it after all required
  fields are saved. Do not implement AI calls here.
- Schedule helpers must never coerce external IDs to numbers. Log/schedule list
  helpers must have conservative default and maximum limits.
- Avoid querying joined-table filters using `.eq('foreignTable.column', ...)`.
- Do not introduce API route handlers, React hooks, Realtime subscriptions, Storage,
  Supabase Auth, or client-side writes.

## Security requirements

- Never expose `SUPABASE_SERVICE_ROLE_KEY` to browser code, serialized props, logs,
  errors, or `NEXT_PUBLIC_*` variables.
- Mark privileged client and service query modules with `import "server-only"` so a
  client-side import fails at build time.
- Validate required env variables when the relevant client is constructed; do not
  read or print secret values.
- Keep all six public-schema tables protected by explicit RLS and grants. The service
  role bypasses RLS and must remain in developer-controlled server code only.
- Public readers receive only active source metadata, analyzed articles, and the
  analysis belonging to analyzed articles. Operational logs/schedule data and all
  mutations remain inaccessible to `anon` and `authenticated` roles.
- Do not use `SECURITY DEFINER`, public executable helper functions, Supabase Auth
  policies, `auth.role()`, unsafe SQL interpolation, or views that could bypass RLS.
- `.env.example` contains placeholders only. Do not modify or commit `.env.local`.
- Pin the dependency version and commit the npm lockfile.

## Acceptance criteria

- A new Supabase project can apply `supabase/schema.sql` without destructive steps
  and receives all six required tables, constraints, indexes, explicit grants, RLS,
  and public-read policies.
- `supabase/schema.sql` and the initial migration are semantically identical and do
  not contain pgvector/embedding work.
- Anonymous access can read only active sources, analyzed articles, and matching
  analyses; it cannot mutate data or access logs/scheduler tables.
- The server-only service client can perform required pipeline CRUD without exposing
  its key.
- Required article data and analysis ranges/labels/percentage totals are enforced by
  Postgres, with original/canonical URL dedupe and one analysis per article.
- Large Oxylabs IDs round-trip as exact strings.
- TypeScript callers receive typed rows/inserts/updates and typed joined article
  projections with no `any`.
- Query modules cover active source selection, public analyzed feed/detail reads,
  chunked URL dedupe, append-only article insertion, analysis persistence/completion,
  structured logs, and scheduler/run tracking without implementing the surrounding
  pipeline.
- The current fixture-backed UI and Clerk integration remain unchanged.
- Documentation clearly distinguishes applying the SQL to Supabase from merely
  checking source files locally.

## Exact manual test steps expected after implementation

1. In Supabase Dashboard, open SQL Editor for the intended project, paste the full
   contents of `supabase/schema.sql`, and run it once.
2. Paste and run `supabase/verify.sql`. Confirm all six tables report RLS enabled,
   the expected policies/grants exist, required constraints/indexes are present, and
   the verification queries return no failing rows.
3. In Project Settings -> API (or Connect), copy the project URL, public anon key,
   and server secret/service-role key into `.env.local` using the names in
   `.env.example`. Never paste the service key into a `NEXT_PUBLIC_*` variable.
4. Run `npm install`, then `npm run dev` from `E:\Projects\skew_news`.
5. Use a public-key REST request to `GET /rest/v1/sources?select=id,name,listing_url,logo_url&is_active=eq.true`
   with `apikey` and `Authorization: Bearer <anon-key>` headers. Confirm `200` and an
   empty array or active sources only.
6. Repeat against `/rest/v1/logs?select=id&limit=1` with the anon key and confirm the
   request is denied, proving operational data is not public.
7. Attempt a harmless anon insert into `sources` inside a transaction or with a
   disposable row and confirm it is denied. Do not add real source URLs during this
   authorization check.
8. Use the Dashboard Table Editor or SQL Editor as an administrator to add a
   temporary valid source, article, and analysis whose percentages total 100. Confirm
   an unanalyzed article is hidden from the anon article query, then set a complete
   analysis and `analyzed_at` and confirm it becomes readable.
9. Attempt an invalid analysis whose percentages do not total 100 and confirm the
   database rejects it. Attempt duplicate `original_url` and non-null
   `canonical_url` values and confirm the database rejects duplicates.
10. Insert an Oxylabs schedule/run ID longer than JavaScript's safe integer range as
    text through the SQL Editor, read it back, and confirm every digit is unchanged.
11. Remove only the temporary smoke-test rows in dependency-safe order after the
    checks. This cleanup is manual and must target the exact IDs created in step 8.
